Case study · TRANSFLO Mobile+

Shipping Flutter inside a native Android app — without a rewrite

How we brought Flutter features into a mature Kotlin codebase used by truck drivers across the US, while the native flows kept running untouched.

  • RoleSenior Android Engineer — integration architect
  • AppTRANSFLO Mobile+ · 500K+ downloads
  • StackKotlin, Flutter, MethodChannel, deep links
  • Timeline2023 – Present

The problem

TRANSFLO Mobile+ is the flagship B2B app for US truck drivers: document scanning, load management, ELD integration and trucking-optimized navigation. The Android app is a large, established Kotlin codebase that drivers rely on every day, so a full rewrite was not an option.

At the same time, the business wanted to deliver new features across platforms faster. The answer was Flutter add-to-app: build new features once in Flutter and embed them inside the existing native app, next to the screens that already worked.

Constraints

  • No regressions in native flows. Scanning, load management and ELD had to keep working exactly as before.
  • Drivers are often offline. Coverage on the road is patchy, so actions taken inside Flutter screens could not be lost when the network dropped.
  • One navigation story. Users, push notifications and other apps needed to reach a screen without caring whether it was native or Flutter.
  • Two runtimes, one source of truth. Native and Flutter code had to share state, such as scan results, without drifting out of sync.

Architecture

1. Native stays the host

The Android app stays in charge of startup, navigation and lifecycle. Flutter is added as a module and shown only where a feature is built in Flutter. Existing native flows don't change at all, which kept the risk of each release low.

2. MethodChannel bridges with a narrow contract

Native and Flutter code talk through MethodChannel bridges. Each bridge does one clear job instead of being a general-purpose pipe. That keeps the contract between the two runtimes small, easy to review and testable from both sides.

3. A singleton scan-result channel

Document scanning is native and central to the product, but Flutter features need its results too. A single singleton channel carries scan results between the two runtimes. That gives one source of truth for scan state and avoids duplicate listeners or results arriving twice when screens are re-created.

4. Deep-link routing across both worlds

All entry points go through the app's transflomobileplus:// deep-link scheme. A single router decides whether a link opens a native screen or a Flutter route. Notifications, other apps and in-app navigation therefore never need to know which technology a screen uses, and a feature can move between native and Flutter without breaking its links.

5. Offline action synchronization

Drivers lose signal often. Actions started in Flutter screens are handed to the native side, which queues them and syncs them to the backend once the device is back online. That way drivers get the same offline guarantees whether a screen is native or Flutter.

Outcome

  • New features can be built in Flutter and shipped inside the existing app, with no rewrite of the native flows drivers depend on.
  • One deep-link and navigation model covers native and Flutter screens.
  • Offline behavior is the same across both runtimes, which matters for a workforce that is on the road.
  • A clear, small bridge contract that other engineers on the team can extend safely.

What I'd tell another team starting add-to-app: decide early which side owns navigation and offline state. Keep the channel contract small and explicit, because everything else is easier to change later.
